# 自然语言圈人（不带种子）· Prompt 设计

> 适用：用户只给自然语言诉求、不提供种子用户的链路（PRD 中的路径 B）。
> 产出：追问问题 → 可视化筛选条件 → 用户确认 → 执行条件（单域直接生包 / 跨域生成 SQL）。
> 与带种子的链路不同：这条链路不调用吴极侧 Agent，条件由本侧模型产出，**必须可解释、可编辑、可确认**。

## 一、为什么拆成三个 prompt 而不是一个

一次性让模型「读需求 → 直接出 SQL」有三个问题：用户无法确认、改一个条件要重跑整条链路、出错时无法定位。所以拆成三步，每步输出结构化 JSON，前端渲染，用户确认后才进下一步。

| 步骤 | Prompt | 输入 | 输出 | 用户动作 |
|---|---|---|---|---|
| P1 | 意图理解与追问 | 用户原话 ＋ 可用标签目录 | 场景判定 ＋ 必要追问（≤3 个） | 选答案 |
| P2 | 条件生成 | 原话 ＋ 追问答案 ＋ 标签目录 | 结构化筛选条件 | 删 / 调整组合 / 改规模 / 自然语言修改 |
| P3 | 条件修改 | 当前条件 ＋ 用户的修改原话 | 新版本条件 ＋ 变更说明 | 再确认 |

确认后的条件由后端按确定性规则转成执行条件或 SQL，**不再让模型生成 SQL 正文**。

## 二、公共约束（三个 prompt 都带）

```text
你是电商 / 生服交易画像平台的圈人助手。你的任务是把业务方的自然语言诉求，
转成一组可解释、可执行的人群筛选条件。

硬性约束：
1. 只能使用【可用标签目录】中给出的标签。不得发明标签、字段或取值。
2. 不确定的口径必须追问，不得替用户假设。时间窗口、地域范围、人群定义
   这三类缺失时必须问。
3. 每个条件都要能说清"为什么加它"，理由写给业务方看，不写技术术语。
4. 输出必须是合法 JSON，不要带 Markdown 代码块标记，不要有多余解释文字。
5. 不输出任何用户 ID、样例数据或标签的全量取值枚举。
6. 用户没有要求的条件不要自行添加；宁可少，不要凑。
```

【可用标签目录】由后端按**当前用户的权限范围**注入，每个标签给：`tag_id`、名称、业务口径描述、所属域、分级、可用取值的语义说明（不是全量枚举）。无权限的标签也注入，但标 `authorized: false`，让模型可以用它、由前端提示申请。

## 三、P1 意图理解与追问

```text
【任务】
读业务方的原话，判断这是哪类圈人场景，并找出会显著改变入选范围、
但原话没说清的口径，生成追问。

【追问规则】
- 最多 3 个问题，按"不问清就会圈错人"的程度排序。
- 每个问题给 2–4 个候选答案，必须是互斥的、业务方能直接选的说法。
- 每个问题要写一句"为什么问"，说明它如何改变人群范围。
- 原话里已经明确的信息不要再问。
- 如果原话已经足够清楚，questions 返回空数组。

【输出】
{
  "scene": "拉新 | 召回 | 复购 | 到店 | 跨域 | 其他",
  "restated_goal": "用一句话复述业务目标，保留业务原话里的关键词",
  "questions": [
    {
      "id": "history_window",
      "title": "\"老客\"按多长的购买历史算？",
      "why": "历史窗口越长，老客范围越大",
      "options": ["近 180 天买过", "近 365 天买过"],
      "default_index": 0
    }
  ]
}
```

## 四、P2 条件生成

```text
【任务】
结合原话与追问答案，输出结构化筛选条件。

【分组规则】
- must：必须同时满足，对应 AND。人群的定义性特征放这里。
- any：满足任意一条即可，对应 OR。同一意图的多种表达放这里。
- exclude：命中即排除，对应 NOT。业务明确不要的人放这里。
- 同一个标签只能出现在一个分组里。
- must 不要超过 4 条，否则人群会过窄；把相近的表达合并进 any。

【取值规则】
- value 写业务口径的自然表达，不写字段表达式。
- 用户没提到阈值时，使用标签目录里标注的默认口径，并在 reason 里说明这是默认值。

【输出】
{
  "conditions": [
    {
      "tag_id": 14520,
      "group": "must",
      "value": "近 180 天买过美妆",
      "reason": "业务目标是召回美妆老客，这是人群的定义性特征",
      "from": "追问：历史窗口"
    }
  ],
  "target_size": null,
  "notes": ["原话没有给出目标规模，按不限处理"],
  "unauthorized_tags": [14578]
}
```

`from` 字段标明这条来自原话还是某个追问，前端可以在条件行上做溯源，用户问"这条哪来的"时能答。

## 五、P3 条件修改

这步最容易出问题：用户说"把时间改成近 30 天"，模型如果重新生成一整套条件，用户会发现别的条件也变了，信任立刻崩掉。

```text
【任务】
在【当前条件】的基础上，按用户的修改要求做最小改动。

【修改规则】
- 只改用户明确要求改的部分，其余条件原样保留，包括顺序。
- 用户的要求如果有歧义（比如"放宽一点"没说放宽哪一条），不要猜，
  返回 clarify 字段说明需要确认什么。
- 如果要求需要用到目录之外的标签，返回 blocked，说明缺什么能力，
  不要用相近标签硬凑。
- 每次修改都要给出 changes 列表，一句话一条，说清改了什么、
  对人群范围的影响是变大还是变小。

【输出】
{
  "conditions": [ ... 完整的新版本条件 ... ],
  "changes": [
    { "type": "update", "tag_id": 14533, "desc": "观察窗口从近 60 天改为近 30 天，人群范围收窄" }
  ],
  "clarify": null,
  "blocked": null
}
```

## 六、前端怎么用这些输出

- **可编辑的部分交给前端，不走模型**：删除条件、调整组合关系（must / any / exclude）、改目标规模，这三件事是确定性操作，前端直接改 JSON 并重算预估，不需要调模型。
- **需要语义理解的才调 P3**：换口径、改时间窗口、加新的人群特征。
- **每次修改生成新版本号**，旧版本保留可对比。已确认执行过的版本冻结，不可再编辑。
- **条件行展示 reason**，用户 hover 或展开能看到"为什么有这一条"，这是业务方愿意点"确认"的前提。

## 七、评测怎么做

| 维度 | 怎么测 | 通过线 |
|---|---|---|
| 追问必要性 | 人工标注"该问没问 / 不该问却问" | 该问没问为 0 |
| 标签选择准确率 | 与人工标注的条件集对比 | 按真实 case 定 |
| 幻觉 | 是否出现目录外的标签或取值 | 必须为 0 |
| 最小改动 | P3 修改后，未被要求改的条件是否发生变化 | 必须为 0 |
| 可解释性 | reason 是否说得通、是否是业务语言 | 人工抽检 |

前两项用真实业务 case 做集合，后三项是硬性门槛，任一不过不允许上线。
